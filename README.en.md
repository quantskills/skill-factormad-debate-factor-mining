This is not a factor library or a backtest engine. It is a **FactorMAD-style LLM multi-agent debate skill** for turning "generate a code-based stock alpha factor" into a runnable, checkable, and auditable workflow.

`role: skill` `platform: codex` `category: tooling` `status: active` `validation: runnable` `output: factor-candidates` `paradigm: llm multi-agent debate`

---

`skill-factormad-debate-factor-mining` is a self-contained QUANTSKILLS community skill. It follows the core idea of the FactorMAD paper: two LLM agents debate, critique, and revise candidate factors, then export candidates as executable Python functions instead of restricting factor discovery to a predefined operator set.

This repository provides a research workflow that starts from OHLCV market data, generates candidate factor code, performs basic code validation and lightweight IC/ICIR evaluation, then writes auditable JSON artifacts.

## What Problem This Skill Solves

Common failure modes in automated factor mining include:

- **Formula without executable code**: generated expressions are hard to plug into a research pipeline.
- **One-shot LLM generation without critique**: there is no opposing view or iterative repair.
- **Generated code cannot run**: NaN, inf, index misalignment, zero volume, and look-ahead risks are not checked.
- **Results are not auditable**: users cannot trace each candidate, debate view, filtering result, and best factor.
- **Lightweight metrics are overused**: IC/ICIR are internal screening signals, not portfolio-level validation.

This skill provides:

- a FactorMAD-style two-agent debate workflow;
- code-based factor generation that exports a Python function plus arguments;
- basic factor-code debug and validation checks;
- lightweight IC/ICIR candidate screening;
- timestamped output directories for auditable run artifacts;
- `dry_run` mode to validate installation and output contracts without calling an LLM.

## Workflow

```text
1. Prepare an OHLCV market_data.csv file.
2. Prepare an input JSON. The public example uses dry_run=true for mechanical validation.
3. For real runs, copy the example config, configure API credentials through .env or shell variables, and set dry_run=false.
4. Two LLM agents generate, critique, and revise candidate factors.
5. The runtime validates candidate factor code and computes lightweight IC/ICIR metrics.
6. The CLI writes debate records, accepted factors, and the best generated factor.
7. Use independent workflows for out-of-sample checks, costs, risk exposure, and portfolio-level backtests.
```

Default command:

```bash
python scripts/factormad_debate_factor.py --input examples/debate_input.json
```

The public example writes to:

```text
outputs/debate_example/
```

If `output_dir` is not set in the input JSON, the default output directory is:

```text
outputs/debateYYYYMMDDHHMMSS/
```

## Input Requirements

At minimum, provide a market CSV:

- It must contain `date` and `symbol`.
- Real factor evaluation requires `open`, `high`, `low`, `close`, and `volume`.
- `amount` is optional; when missing, the runtime creates it as `close * volume`.
- `vwap` is optional; when missing, the runtime creates it as `amount / volume`. It applies `adjfactor` only when the original CSV already contains `amount` and also provides `adjfactor`.
- The data must be data the user has the right to use.
- `date` should use `YYYY-MM-DD` or another pandas-parseable date format.
- `symbol` is used as the cross-sectional grouping key; each trading day should include multiple stocks.
- `label_config.price` must exist after runtime normalization. For example, `vwap` can be generated by the fallback logic above.

Example input file:

```text
examples/debate_input.json
```

See the full schema in:

```text
references/input_schema.md
```

Real LLM runs require local credentials. Recommended:

```bash
cp .env.example .env
# edit .env, fill OPENAI_API_KEY or FACTORMAD_OPENAI_API_KEY
```

Shell environment variables are also supported:

```bash
export OPENAI_API_KEY=...
export OPENAI_MODEL=gpt-4o-mini
export OPENAI_BASE_URL=https://api.openai.com/v1
```

Credential priority is `FACTORMAD_OPENAI_*` > `OPENAI_*`. The runtime loads the repository-root `.env` with `override=False`, so already exported shell variables are not overwritten. `.env` is ignored by Git; do not commit real credentials.

## Quick Start

Install dependencies:

```bash
python -m pip install -r requirements.txt
```

Run the dry-run example without calling an LLM:

```bash
python scripts/factormad_debate_factor.py \
  --input examples/debate_input.json
```

A successful dry run prints a summary similar to:

```json
{
  "ok": true,
  "dry_run": true,
  "debate_json_path": "outputs/debate_example/factormad_debate_result.json",
  "accepted_factors_path": "outputs/debate_example/accepted_factors.json"
}
```

To force an output directory from the command line:

```bash
python scripts/factormad_debate_factor.py \
  --input examples/debate_input.json \
  --output outputs/debate
```

You can also set it in the input JSON:

```json
{
  "output_dir": "outputs/debate_example"
}
```

Priority is `--output` > `output_dir` > timestamped default directory.

Before a real run, copy a local input config instead of editing the public example directly:

```bash
cp examples/debate_input.json examples/my_debate_input.local.json
cp .env.example .env
# edit .env, fill OPENAI_API_KEY or FACTORMAD_OPENAI_API_KEY
```

Then set `dry_run` to `false` and update `market_data_csv_path`, time ranges, and label settings for your data:

```bash
python scripts/factormad_debate_factor.py \
  --input examples/my_debate_input.local.json
```

`*.local.json` and `.env` are ignored by Git.

During real runs, the CLI prints visible progress such as market data loading, seed factor evaluation, debate job initialization, per-round status, and final accepted / invalid counts.

## Input Variables

`examples/debate_input.json` is the main CLI configuration. Data and seed-file relative paths are first resolved relative to the input JSON directory, then the repository root, then the current working directory. Relative `output_dir` values are resolved from the repository root.

### Basic Fields

| Field | Type | Description |
| --- | --- | --- |
| `market_data_csv_path` | string | Market CSV path. Must contain `date` and `symbol`; real runs require OHLCV and volume fields. |
| `dry_run` | boolean | When `true`, validate inputs, paths, and output contracts without calling an LLM. Set to `false` for real mining. |
| `output_dir` | string | Optional output directory used when `--output` is not passed. CLI output takes precedence. |
| `insample_time_range` | list[string, string] | In-sample range used for `IC` and `ICIR`. |
| `outsample_time_range` | list[string, string] | Out-of-sample range used for `O-IC` and `O-ICIR`. |
| `test_debug_range` | list[string, string] | Short range used for factor-code debug checks. Legacy `test_range` is still accepted. |
| `test_symbols` | list[string] | Symbols used during debug checks. Empty list means all symbols from the CSV. |
| `demo_symbol` | string | Optional single-symbol example. Leave empty for runtime defaults. |

### Labels And Factor Requirement

| Field | Type | Description |
| --- | --- | --- |
| `label_config.price` | string | Price column used for future-return labels, such as `close` or `vwap`. Must exist after runtime normalization. |
| `label_config.span` | integer | Prediction horizon, in rows/periods. |
| `label_config.preprocess` | string | Label preprocessing. Common value is `cs_zscore`, daily cross-sectional z-score normalization. |
| `factor_requirement` | string | Plain-text factor-mining requirement inserted into LLM prompts, such as market, style, forbidden fields, or research constraints. |

`cs_zscore` means de-mean and divide by standard deviation across stocks for each trading day. It reduces the effect of broad market moves on IC evaluation.

### Seed Factors

| Field | Type | Description |
| --- | --- | --- |
| `examples` | list[object] | Inline seed factors. Each item contains `code` and `arguments`. |
| `seed_factors_json_path` | string | External seed factors JSON path. |
| `seed_alphas_json_path` | string | Backward-compatible seed alpha JSON path. |
| `agent_few_shots` | integer | Number of few-shot factors sampled for each agent. |

If `examples` and seed files are empty, the runtime uses built-in default seed factors. For real research, maintain your own seed factors so agent initialization matches your market and research style.

### Debate Controls

| Field | Type | Description |
| --- | --- | --- |
| `llm_name` | string | Model name. If empty, the runtime reads `FACTORMAD_OPENAI_MODEL`, then `OPENAI_MODEL`, then falls back to `gpt-4o-mini`. |
| `debate_jobs` | integer | Number of independent debate jobs. Use `1` for first real runs. |
| `debate_max_rounds` | integer | Maximum debate turns per job. |
| `debate_max_tokens` | integer | Token budget per agent-pair conversation. |
| `seed_metric_threshold` | number | Early-stop threshold for seed-generated factor quality. |
| `factor_metric_threshold` | number | Metric threshold for admitting new factors to the accepted set. |
| `factor_correlation_threshold` | number | Similarity threshold against already accepted factors. Higher similarity is marked `similar`. |
| `key_metric` | string | Primary ranking and filtering metric, usually `ICIR`. |

Recommended first real-run settings:

```json
{
  "debate_jobs": 1,
  "debate_max_rounds": 2,
  "agent_few_shots": 3,
  "key_metric": "ICIR"
}
```

After the flow is stable, increase `debate_jobs` and `debate_max_rounds` gradually.

### Factor Library Variables

| Field | Type | Description |
| --- | --- | --- |
| `use_factormad_alpha_library` | boolean | Whether to read and update a local FactorMAD factor library. |
| `few_shot_from_library` | boolean | Whether to add effective library factors to agent few-shot initialization. |
| `factormad_alpha_library_path` | string | Factor library JSON path. Empty value uses the default path. |

`alpha_library_path` is a legacy compatibility alias. New configs should use `factormad_alpha_library_path`.

Recommended local-library config:

```json
{
  "use_factormad_alpha_library": true,
  "few_shot_from_library": true,
  "factormad_alpha_library_path": "examples/factormad_alpha_library/my_library.local.json"
}
```

The library stores only effective factors that pass lightweight screening. It does not store every invalid or similar candidate. This repository commits only a sanitized sample `examples/factormad_alpha_library/library.json`; for real research, copy the library to a local ignored path before enabling updates.

## Output Artifacts

The public example writes:

```text
outputs/debate_example/
├── factormad_debate_result.json
├── debate_rounds.json
└── accepted_factors.json
```

If neither `output_dir` nor `--output` is set, the CLI uses the timestamped directory `outputs/debateYYYYMMDDHHMMSS/`.

| File | Purpose |
| --- | --- |
| `factormad_debate_result.json` | Main result with `best_factor`, `debate_rounds`, `accepted_factors`, counts, and artifact paths. |
| `debate_rounds.json` | Per-round agent views, candidate factors, statuses, and errors. |
| `accepted_factors.json` | Current accepted set. Real runs include evaluated seed/library factors plus newly generated effective factors. |

Main result fields:

| Field | Description |
| --- | --- |
| `ok` | Whether the run produced a usable result. |
| `job_count` | Number of debate jobs. |
| `round_count` | Total debate round count. |
| `generated_factors` | All factors generated by debate jobs, including effective, similar, and invalid candidates. |
| `accepted_factors` | Current accepted set, including evaluated seed/library factors and newly generated effective factors. |
| `invalid_factors` | Rejected candidates or near-duplicates. |
| `best_factor` | Best candidate from `generated_factors` ranked by `key_metric`; not a final tradable factor. |
| `metric_time_ranges` | Run-level mapping from metrics to sample windows. |
| `library_update` | Library write statistics when the factor library is enabled. |
| `llm_fee` | Runtime-estimated LLM call fee. |

Each factor record uses canonical fields:

| Field | Description |
| --- | --- |
| `name` | Factor name. |
| `code` | Executable Python factor function code. |
| `entry_function` | Entry function name. |
| `arguments` | Arguments used when calling the factor function. |
| `metric` | `IC`, `ICIR`, `O-IC`, and `O-ICIR`. |
| `insample_time_range` | In-sample evaluation range. |
| `outsample_time_range` | Out-of-sample evaluation range. |
| `status` | `effective`, `similar`, `invalid`, `dry_run`, and related statuses. |
| `job_index` | Debate job index that produced the factor. |
| `round` | Debate round that produced the factor. |

## Project Status And Boundaries

- **Project status**: Community Project, not officially reviewed, certified, or endorsed by QUANTSKILLS.
- **Platform**: Codex only (`platforms: [codex]`).
- **Data source**: This repository includes toy data only. Real data is user-provided, and users are responsible for data licensing and compliance.
- **Core assumption**: Daily OHLCV cross-sectional factor research. Lightweight IC/ICIR is used for candidate screening.
- **Known limitations**: No transaction costs, market impact, suspension/liquidity modeling, industry/style exposure control, portfolio constraints, or real execution modeling.
- **Risk boundary**: Historical statistics do not imply future performance. LLM-generated code requires human review and independent validation.
- **Use**: For quantitative research, education, and methodology reference only. Not investment advice, trading signals, or profit assurance.
